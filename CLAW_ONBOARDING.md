# 🛠️ Claw Engine: Implementation Onboarding Guide

## 🎯 Mission
The objective is to transform the `claw/` repository from its current OpenCLAW-derived state into a **Minimal, High-Performance Cellular Agent Engine**. 

A "Claw" is the fundamental unit of cellular programming: an autonomous, intelligent actor that lives within a single spreadsheet cell (or partitioned memory slot), interacts with its environment via triggers, and can dynamically equip modules to expand its capabilities.

## 🏗️ Architectural Core: The Actor Model
The engine must implement a lightweight **Actor Model**. 
- **Isolation:** Each Claw instance is strictly isolated.
- **Communication:** Interaction occurs via defined protocols (WebSocket/REST) or social relationships (Master/Slave/Co-worker).
- **Lifecycle:** `DORMANT` ➔ `THINKING` ➔ `PROCESSING` ➔ `DORMANT` (with error handling to `ERROR` state).

## 📜 Technical Specification (The Schema)

Implementation must strictly adhere to the [Core Claw Schema](https://github.com/SuperInstance/polln/claw/schemas/claw-schema.json). Below are the critical type-mapping requirements for the Rust implementation.

### 1. Identity & Model (`ModelConfiguration`)
Every Claw must be uniquely identifiable and have a defined intelligence source.
| JSON Property | Rust Type | Description |
| :--- | :--- | :--- |
| `id` | `uuid::Uuid` | Unique instance ID. |
| `model.provider` | `enum ModelProvider` | `deepseek`, `openai`, `anthropic`, `ollama`, `custom`, etc. |
| `model.model_name`| `String` | The specific model string (e.g., `"deepseek-chat"`). |
| `model.parameters`| `HashMap<String, Value>`| Inference params (temp, top_p, max_tokens). |

### 2. Behavior & Purpose (`SeedReference`)
Claws do not have hardcoded logic; they have **Seeds**.
- **Seed:** A prompt-based behavioral definition.
- **Implementation:** The engine must resolve a `seed_id` to a set of instructions/prompts and apply them to the `model`.

### 3. The Equipment System (`EquipmentModule`)
This is the core of Claw's extensibility. Claws "wear" modules.
- **Slots (`EquipmentSlot`):** `MEMORY`, `REASONING`, `CONSENSUS`, `SPREADSHEET`, `COORDINATION`, etc.
- **Dynamic Loading:** The engine must support equipping/unequipping modules at runtime without restarting the Actor.
- **Module Config:** Each module provides a `config` object used to initialize its internal state.

### 4. Social Architecture (`ClawRelationships`)
Claws are not lone actors; they form structures.
- **Master-Slave:** A Master Claw delegates sub-tasks to "Slave" Claws.
- **Co-workers:** Peer Claws participating in `CONSENSUS` or collaborative reasoning.

### Phase 2: The Trigger & Loop (The Heartbeat)
- [ ] Implement the `TriggerConfiguration` logic (Periodic, Event-based, Data-driven).
- [ ] Develop the main execution loop: `Wait for Trigger` ➔ `Transition to THINKING` ➔ `Inference` ➔ `Transition to PROCESSING` ➔ `Action` ➔ `Transition to DORMANT`.

### Phase 3: The Equipment Manager (The Muscle)
- [ ] Create the `EquipmentRegistry`.
- [ ] Implement the logic for loading/unloading modules based on `equipment` array in the schema.
- [ ] Ensure module-specific `config` is correctly passed during initialization.

### Phase 4: Interface & Integration (The Nervous System)
- [ ] Expose the engine via a high-performance WebSocket server.
- [ ] Provide a REST API for management and state inspection.
- [ ] (Optional) Implement TypeScript bindings for seamless `spreadsheet-moment` integration.
